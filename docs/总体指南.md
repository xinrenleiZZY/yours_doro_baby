# doro 桌面宠物 · 企业级标准与总体指南

> 本文件是项目的「总纲」：定义什么叫企业级标准、如何持续核验、用什么指标衡量、以及目标如何变更。
> 配套文档：
>
> - `docs/项目核验报告.md`：对当前代码库按本指南逐项打分，并列出缺陷清单。
> - `docs/优化路线图.md`：把缺陷与改进项排成 P0/P1/P2 的可执行方案。

## 2. 企业级标准基线（六维评分卡）

每个维度按 0–5 分评估，5 = 达到可对外交付的企业级基线。评分只描述「是否具备」，不代表功能多寡。

| 维度                    | 关键评分项                                                                                               | 权重 |
| ----------------------- | -------------------------------------------------------------------------------------------------------- | ---- |
| A. 工程规范与可交付     | README、LICENSE 文件、CHANGELOG、`.gitignore`、Lint/格式化、依赖锁定与审计、可打包安装包、版本与发版流程 | 20%  |
| B. 稳定性与安全         | 存档可靠性与迁移、崩溃恢复/错误日志、IPC 入参校验、进程隔离与 CSP、单实例、退出清理、依赖漏洞            | 20%  |
| C. 自动化测试与质量门禁 | 单元测试、集成/冒烟测试、测试稳定可重复、CI 门禁、覆盖率基线                                             | 15%  |
| D. 体验与美术           | 动画与交互反馈完整性、视觉一致性、无动画错位、性能（帧率/启动/内存）、资源体积预算、无障碍、音效         | 15%  |
| E. 玩法与增长           | 数值平衡、玩法深度、离线/留存机制、成就或装扮等长线目标、可选埋点指标                                    | 15%  |
| F. 文档与协作           | 架构说明、开发/构建指南、贡献与评审流程、License 合规与素材来源登记                                      | 15%  |

**评分口径**

- 0：缺失；1：雏形；2：部分具备但不成体系；3：基本具备、有可查证据；4：完善、有自动化保障；5：企业级并可持续演进。
- 综合分 = Σ(维度分 × 权重)。**达标线：综合分 ≥ 3.5 且无任何维度 < 2。**

## 3. 持续核验流程（循环）

每轮核验按同一套动作执行，产出写回文档，保证「可追溯、可重跑」。

1. **取基准**：确认当前版本号、最近变更、工作区状态（是否存在未清理的构建/调试产物）。
2. **静态审计**：逐维度对照第 2 节评分项，采集证据（文件是否存在、脚本是否可执行）。
3. **动态验证**：跑可执行的自动化检查——
   - `npm test`（`node tools/test-game.js`）单元测试必须全绿。
   - 冒烟测试 `node_modules/.bin/electron tools/smoke-test.js` 必须全绿且连续 3 次稳定（见第 5 节门禁）。
4. **打分与缺陷登记**：更新 `docs/项目核验报告.md`，记录新增/已修缺陷与证据。
5. **重排方案**：更新 `docs/优化路线图.md`，把新缺陷/新目标落到 P0/P1/P2。
6. **回写指南**：若标准或目标发生变化，更新本文件并记录变更原因。

> 本循环不追求一次性完成，而是「每轮都有产出、每轮都比上轮更接近达标」。

## 4. 任务指标（KPI 与质量门禁）

### 4.1 质量门禁（硬性，必须全绿才算「可交付」）

| 编号 | 门禁         | 通过标准                                       |
| ---- | ------------ | ---------------------------------------------- |
| G-1  | 单元测试     | `npm test` 全绿                                |
| G-2  | 冒烟测试     | 全绿，且连续 3 次无波动                        |
| G-3  | 存档往返一致 | 存→读后状态与写入值一致（含异常/损坏存档兜底） |
| G-4  | 依赖安全     | `npm audit --omit=dev` 无 high/critical        |
| G-5  | 打包         | 能产出一个可安装/可运行产物并成功冷启动        |
| G-6  | 静态规范     | Lint 0 error、格式化已统一                     |
| G-7  | 仓库洁净     | 无构建/调试产物入库（`.gitignore` 生效）       |

### 4.2 体验指标（期望值，可「美化」上调）

| 指标                       | 当前基线                     | 企业级目标                                             |
| -------------------------- | ---------------------------- | ------------------------------------------------------ |
| 冷启动到可交互             | 395ms                        | ≤ 1.5s                                                 |
| 常驻内存占用（私有工作集） | 约 105MB                     | ≤ 150MB（含共享 DLL 的总工作集约 300MB，不作验收口径） |
| 窗口动画帧率               | 87fps                        | ≥ 50fps                                                |
| 安装包体积                 | 157.6MB                      | ≤ 180MB（Electron 44 + 49MB 动作资源，含资源）         |
| 关键操作反馈               | 喂/玩/升级/摸头均有文字+动画 | 全部含可见动效与音效，且无动画错位                     |

### 4.3 增长指标（可选，需先埋点）

- 次日留存、单次会话时长、离线收益触达率、升级/装扮转化。**在未埋点前不设数值目标**，仅记录「未埋点」状态。

## 5. 目标分级与变更机制

目标分三级，变更权限与记录要求不同：

| 级别           | 含义                          | 变更规则                                                                                          |
| -------------- | ----------------------------- | ------------------------------------------------------------------------------------------------- |
| G0 硬门禁      | 第 4.1 节的 7 条质量门禁      | 只能「从无到有」补齐，**不可下调**；下调需在报告中说明理由并显式标注风险                          |
| G1 期望目标    | 第 4.2/4.3 节的性能与增长指标 | 可「美化」上调（阈值提高）或按实际情况下调；每次变更在 `优化路线图.md` 记录「旧值 → 新值 → 原因」 |
| G2 美化/方向项 | 美术风格、动效、玩法扩展等    | 可自由调整，允许「直接美化目标」或「更改需求目标」；需说明影响面（是否影响已交付体验/存档兼容）   |

**变更记录要求**（任何目标变更都必须留下痕迹）：

1. 在本文件第 4 节改数值/条目；
2. 在 `docs/优化路线图.md` 追加一条变更记录：`日期 · 变更项 · 旧 → 新 · 原因 · 影响面`；
3. 若影响存档结构或用户已有数据，必须在 `docs/项目核验报告.md` 标注「兼容性风险」。

**授权说明**：本指南允许对 G1/G2 目标「直接美化」与「更改需求目标」，无需逐条审批，但必须按上述规则留痕；G0 硬门禁调整需单独确认。
